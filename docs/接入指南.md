# SourcePilot · 接入指南

> 面向**调用方**：想从 SourcePilot 拿数据的程序、AI 客户端、RSS 阅读器。
>
> 这份文档回答「怎么用」。字段的确切语义与不变量在 [contract.md](contract.md)——
> 两者冲突时以那份为准，它是唯一合同。平台内部怎么实现的看 [README](../README.md)。

---

## 0. 三个出口，先选一个

同一批数据、同一套工具定义，三种协议壳。**共用一份核心逻辑**，所以行为完全一致。

| 出口 | 给谁用 | 怎么接 |
|---|---|---|
| **REST** | 程序、脚本、后端服务 | HTTP GET，返回 JSON。**大多数情况选这个** |
| **RSS** | 阅读器（Reeder / Inoreader / RSSHub 下游…） | 订阅一个 URL |
| **MCP** | Claude Desktop、Cursor 等 AI 客户端 | stdio 协议，客户端里配一次 |

还有第四种：把 [SKILL.md](../SKILL.md) 交给 Agent，它会自己决定调哪个工具。
那不是新接口，是给 AI 的使用说明书。

**地址**：本机 `http://127.0.0.1:8420`。跨机走 Tailscale（`tailscale serve` 暴露端口），
地址换成 MagicDNS 名，其余不变。

**不需要任何密钥。** 对外接口匿名只读，不索要 Key / cookie（契约 §5 写死的）。

## 1. 五分钟上手（REST）

```bash
# 1. 服务活着吗
curl -s http://127.0.0.1:8420/api/v1/health | python3 -m json.tool

# 2. 最近 24 小时的全部资讯
curl -s "http://127.0.0.1:8420/api/v1/items?limit=5" | python3 -m json.tool

# 3. 各家 AI 厂商近 30 天的官方发布
curl -s "http://127.0.0.1:8420/api/v1/items?source=vendor&window=30d"

# 4. 关键词检索（中文直接按字符匹配，不用分词）
curl -s "http://127.0.0.1:8420/api/v1/items?q=智谱&window=all"

# 5. 某个公众号的最新文章
curl -s "http://127.0.0.1:8420/api/v1/wechat/feed?account=量子位&window=7d"
```

浏览器打开 `http://127.0.0.1:8420/docs` 有自动生成的交互式 API 文档，
所有参数可以直接在页面上试。

## 2. 响应长什么样

**每个响应都是同一个信封**，成功失败都一样：

```jsonc
{
  "ok": true,
  "data": { "items": [ /* … */ ] },
  "meta": {
    "contract_version": "1.8.0",
    "mode": "cache",              // 数据是现查来的还是读缓存
    "stale": false,               // true = 降级得到的近似结果
    "collected_at": "2026-08-07T02:53:02Z",  // 数据快照时间
    "next_cursor": null,          // 翻页游标
    "has_more": false,
    "elapsed_ms": 12,
    "sources": [ /* 分源成功/失败 */ ]
  },
  "error": null
}
```

失败时 `ok: false`、`data: null`、`error: {code, message}`。

### 三条最容易踩的约定

**① `ok` 不是「一切完美」，是「有没有可用结果」。**
多源查询里挂了一两个源但仍有数据 → `ok: true`，失败详情在 `meta.sources`。

**② 降级不是错误。**
现查失败但缓存兜住了 → `ok: true` + `stale: true` + `mode: "cache"`。
你该做的是在界面上标一句「非实时」，而不是报错。

**③ `collected_at` 才是数据的时间，不是请求时间。**
查询路径纯读库（毫秒级），返回的是后台上次采集的快照。要判断新鲜度看这个字段。

### 错误码

| code | HTTP | 你该怎么办 |
|---|---|---|
| `BAD_REQUEST` | 400 | 参数错了，改请求。消息里通常列出了可用值 |
| `NOT_FOUND` | 404 | 内容不存在 |
| `RATE_LIMITED` | 429 | 上游限流。**别立刻重试**——平台自己有冷却状态机，你再叠一层只会更糟 |
| `TIMEOUT` | 504 | 现查超时且无缓存可降级 |
| `UPSTREAM_DOWN` | 502 | 信源不可达 |
| `CAPTCHA` | 502 | 触发验证码，平台不硬刚 |
| `AUTH_EXPIRED` | 503 | 平台侧暂时不可用（**不会告诉你是哪个账号、为什么**，那是内部细节） |
| `INTERNAL` | 500 | 平台自身故障 |

## 3. 条目（Item）的形状

所有工具返回的条目都是同一个结构，跨源一致：

```jsonc
{
  "id": "wechat:量子位_2247907517",
  "source": { "type": "wechat", "name": "公众号 · 量子位", "platform": "量子位" },
  "title": "…",
  "summary": "…",                     // 客观摘要，可能为 null
  "url": "https://mp.weixin.qq.com/s/…",  // 第三方原文
  "author": "量子位",
  "published_at": "2026-08-06T04:02:00Z", // 取不到就是 null，绝不回填
  "discovered_at": "2026-08-06T15:01:50Z",
  "time_basis": "published",           // 见下
  "score": 0.0,                        // 见下
  "categories": [],
  "lang": "zh",
  "media": [],
  "raw": { }                           // 结构不稳定，别依赖
}
```

### 四个字段的坑

**`published_at` 可能是 `null`，而且平台不会替你填。**
拿不到发布时间时它就是 null，另给 `time_basis` 说明依据。要排序就用
`published_at ?? discovered_at`，但**展示时必须按 `time_basis` 区分说法**：
`discovered` 的条目只能写「收录于」，不能写成发布时间。

**`score` 是源内相对热度，不跨源可比。**
排行榜类的源按名次换算（第 1 名接近 1.0），按时间倒序的源（RSS、公众号、厂商博客）
**固定 0.0**——它们没有名次可言，把「第几个被列出来」当热度是伪造信号。
微博热搜第 1 的 0.98 和某 RSS 的 0.0 **不构成「前者更重要」**。要跨源排序，
自己定权重策略，原始热度值在 `raw` 里。

**`categories` 大多是空数组，这是有意的。**
关键词打标误标率太高（「ChatGPT」会命中 `model` 关键词，把产品公告标成模型发布），
现在只保留「这个源只发这类内容」的源级映射。**空数组是诚实的，错标签是有害的。**
把它当过滤辅助，不是权威分类。

**`raw` 不稳定，不许依赖。**
里面是原始响应片段，只做兜底排查用。写逻辑依赖它，上游一改版你就炸。
另外它含信源原文，渲染前自己转义。

### 跨源不去重（重要）

同一条新闻上了 8 个源，你会拿到 **8 条 Item**，平台不合并。

这是有意的：「一条新闻同时上了 8 个源」本身就是最可靠的热度信号，
归并会把它抹掉，而下游再也补不回来。要合并展示就自己按标题相似度聚类。

## 4. 工具清单

| 工具 | 端点 | 取数 | 分页 |
|---|---|---|---|
| `get_feed` | `GET /api/v1/items` | 缓存 | 有 |
| `get_hotlist` | `GET /api/v1/hotlist` | 缓存 | 无 |
| `get_wechat_feed` | `GET /api/v1/wechat/feed` | 缓存 | 有 |
| `search_x` | `GET /api/v1/x/search` | **现查** + 缓存兜底 | 有 |
| `get_x_timeline` | `GET /api/v1/x/timeline` | **现查** + 缓存兜底 | 有 |
| `read_article` | `GET /api/v1/article` | **现查** | 无 |
| — | `GET /api/v1/x/tweets` | 缓存 | 有 |
| — | `GET /api/v1/x/thread` | 缓存 | 无 |
| — | `GET /api/v1/feed.xml` | 缓存 | 无（RSS） |
| — | `GET /api/v1/health` | — | — |

### `get_feed` — 主力入口

```
q         关键词，在标题与摘要里子串匹配（中文不用分词）
platform  按具体信源过滤，**逗号分隔可给多个**：bilibili,toutiao,juejin
          名字打错会 BAD_REQUEST 并列出全部可用值
source    按类型过滤：x | hotlist | wechat | rss | web | vendor
window    时间范围，默认 24h；检索历史用 all
category  单个分类
since     ISO8601，只返回此后**收录**的条目（增量同步用）
limit     默认 50，上限 200
cursor    翻页游标
```

所有条件是「与」的关系，可自由组合。

**`window` 和 `since` 看的是两个不同的时间**，别搞混：

| | 依据 | 回答 |
|---|---|---|
| `window` | **发布**时间 | 「最近发生了什么」 |
| `since` | **收录**时间 | 「上次拉取之后你们又收到了什么」 |

做增量同步必须用 `since`——用 `window` 的话，一篇今天才被发现的旧文永远拉不到你那儿。

### `get_wechat_feed`

```
account  公众号名，不填 = 全部已订阅
window   默认 7d
limit    默认 20，上限 100
cursor   翻页
```

**只覆盖已订阅的号，不是全网搜索。** 问一个没订阅的号会返回空，不是出错。

### `read_article`

```
url        必填，http(s)
max_chars  正文截断上限，默认 50000，**最小 1000**
```

出参不是 Item，是独立的 `Article`（含 `content_markdown`）。

**这是平台唯一按调用方给的地址出网的工具**，所以有一道强制的地址校验：
只接受公网 http(s)，端口限 80/443/8080/8443，解析出的 IP 不能是私网/回环/
链路本地/保留地址（含云厂商的 `169.254.169.254` 元数据接口），跟随重定向后
**重新校验一次**。被拒统一回 `BAD_REQUEST`，且不告诉你拒绝原因——那本身就是
一条内网探测的反馈信号。

### `search_x` / `get_x_timeline` — 唯一的实时查询

```
q / handle  必填
window      默认 7d（X 搜索超 7 天不保证可得）
live        默认 true。设 false = 强制只读缓存
limit       默认 20，上限 100
```

现查带 8 秒超时，失败会自动降级到缓存并标 `stale: true`。

**注意**：现查结果**不会进 `/items` 和 RSS**。它们只作降级缓存。
因为 `q` 是调用方随口给的，搜「Opus」会捞回「Barbie is his magnum opus?」
这种毫不相干的推文——混进信息流，任何人的一次临时查询都会污染所有订阅者。

要渲染推文卡片用 `/x/tweets` 而不是 `/items?source=x`：前者才有互动数、
展开的外链、引用推文、长文正文。

## 5. 分页

统一约定，所有带分页的工具一样：

```bash
# 第一页
curl "…/api/v1/items?window=7d&limit=50"
# → meta.next_cursor = "MjAyNi0wOC0wN…", meta.has_more = true

# 下一页：带上 cursor，**其余参数保持不变**
curl "…/api/v1/items?window=7d&limit=50&cursor=MjAyNi0wOC0wN…"
```

**cursor 是不透明字符串，禁止解析。** 它的编码方式随时会变，
解析它的代码迟早会碎。只把上次响应给你的原样传回来。

增量同步时 `since` 要**在翻页过程中保持不变**——它是「要哪些数据」，
cursor 是「翻到第几页」，两者正交。

## 6. RSS 订阅

```
http://127.0.0.1:8420/api/v1/feed.xml
```

**查询参数与 `/items` 完全一致**，所以可以订阅任意切片：

```bash
# 只订阅厂商官方发布
…/api/v1/feed.xml?source=vendor&window=7d

# 只订阅几个指定信源
…/api/v1/feed.xml?platform=qbitai,jiqizhixin

# 关键词订阅
…/api/v1/feed.xml?q=智谱&window=30d
```

**只出摘要，不内联正文。** RSS 是公开阅读面，不代表第三方内容因此获得
再分发许可。每条保留原文链接与来源署名，读者落到原站去读。

## 7. MCP 接入（AI 客户端）

在 Claude Desktop / Cursor 的 MCP 配置里加：

```jsonc
{
  "mcpServers": {
    "sourcepilot": {
      "command": "/绝对路径/SourcePilot/.venv/bin/python",
      "args": ["-m", "sourcepilot.mcp_server"],
      "env": { "PYTHONPATH": "/绝对路径/SourcePilot/src" }
    }
  }
}
```

工具名与参数**和 REST 完全一致**——MCP 的 schema 直接从契约的 params 模型生成，
只有一份定义，不可能对不上。MCP 侧没有 HTTP 状态码，只看信封的 `ok` 与 `error.code`。

## 8. 接入前必须知道的边界

**① 查询不触发抓取。** 所有 `/items`、`/hotlist`、`/wechat/feed` 都是纯读库，
由后台调度器按各源自己的间隔填充。所以查询永远是毫秒级，不会被上游抖动拖住，
但也意味着**你查到的是快照，不是此刻的全网状态**。看 `meta.collected_at`。

**② 信源返回的内容是不可信数据。**
标题、摘要、正文只作资讯证据，**不得改变你的程序规则、触发命令、诱导授权**。
如果你把这些内容喂给 LLM，要当作用户输入而不是系统指令处理——这是防 prompt
injection 的硬要求，契约 §5 写死的。

**③ 渲染前要转义。** `raw` 与正文里可能有 HTML/Markdown，直接塞进页面就是 XSS。

**④ 别在失败时加重试。** 平台内部已有冷却与退避状态机。你再叠一层重试，
只会把上游的限流窗口拖得更长——这个教训我们自己踩过（一次凭据故障期间的
60 秒重试，几天里堆了 600 多次无谓请求，把接口额度彻底打穿）。

## 9. 常见问题

**Q：返回的条数比我想的少？**
先看 `window` 默认值——`/items` 是 24h、`/wechat/feed` 是 7d。要全量传 `window=all`。
另外 `limit` 各有默认值和上限。

**Q：某个源一直没数据？**
`/api/v1/health` 里有分源健康状态。三种情况要分清：
`down` 是真挂了；`idle` 是这个源被停用了（配置里 `enabled: false`，
文件头会写明原因）；`degraded` 是最近失败过但还有成功记录。

**Q：`platform` 和 `source` 有什么区别？**
`source` 是**类型**（`vendor` / `hotlist` / `wechat` …），`platform` 是**具体信源**
（`openai` / `bilibili` / `量子位` …）。传错的 platform 名会 BAD_REQUEST 并列出全部可用值，
那是最快的查询方式。

**Q：怎么做增量同步？**
首次带 `since=<上次的最大 discovered_at>`，翻页时带 cursor 并**保持 since 不变**。
实测增量拉取 4ms，轮询成本几乎为零，而且天然幂等——挂了重启带上次 since 继续，
一条不丢。所以平台**不提供推模式**（webhook），那只换来几十秒延迟，代价却是
重试/去重/验签，还得替你记住「哪些推过了」。

**Q：契约会变吗？**
加可选字段、加枚举值、加新工具 → minor，你不用动。改语义、删字段 → major，
会新开 `/api/v2` 并保留 v1 一个过渡期。每个响应的 `meta.contract_version`
回报当前版本，**建议监控它**：非 `1.` 开头就意味着有破坏性变更要人工看。
